## Overview

> **Important:** Nothing on this page is implemented yet. There is no `engine/rhi/` or `engine/render/` module, no
> Vulkan dependency in `vcpkg.json`, and `dg-player` and `dg-editor` run only the simulation loop. This page summarizes
> the design in [DESIGN.md §8](https://github.com/ugokce/Detergine-3D-ECS-Game-Engine/blob/main/docs/DESIGN.md#8-rendering)
> so you know what to expect and where your code will plug in.

Rendering is part of the **presentation layer**. It reads the simulation, never writes it, and is compiled out of
headless builds. The planned stack, from bottom to top:

| Layer | Module (planned) | Role |
|---|---|---|
| RHI | `dg::rhi` in `engine/rhi/` | Thin, Vulkan-shaped abstraction. The only code allowed to include `vulkan.h`. |
| Render graph | `dg::render` in `engine/render/` | Per-frame graph of passes with declared reads and writes. Handles barriers, transient memory and culling of unused passes. |
| Render world | `dg::render` | A double-buffered copy of everything visible, extracted from the presentation world each frame. |
| Pipelines | `dg::render` | Desktop visibility-buffer path, mobile forward+ path, 2D sprites, GI tiers. |
| Render features | plugins | `IRenderFeature` implementations that add passes at named extension points. |

Target graphics APIs are Vulkan 1.3 on desktop and Vulkan 1.1+ on Android. macOS and iOS run Vulkan through MoltenVK or
KosmicKrisp. Shaders are written in **Slang** and compiled to SPIR-V.

## Design

### RHI

The **RHI** (render hardware interface) is a thin layer over Vulkan, so the rest of the engine never includes
`vulkan.h` (a CLAUDE.md architecture rule). It is kept close to Vulkan on purpose, which leaves room for a native Metal
backend later if MoltenVK becomes a limit.

* **Bindless resources**: one global descriptor heap, using descriptor indexing or `VK_EXT_descriptor_buffer` where it
  is available. Shaders refer to resources by 32-bit indices.
* Dynamic rendering, `synchronization2`, timeline semaphores, and async compute and transfer queues where the device
  has them.
* 2–3 frames in flight. Destruction is deferred through a queue keyed by timeline value.
* A pipeline cache persisted per device and driver, plus a PSO pre-warm list generated by the cooker.
* **Capability tiers** detected at startup: `Mobile`, `Desktop` and `DesktopRT` (ray query available). On macOS the tier
  depends on what the MoltenVK or KosmicKrisp version exposes.
* GPU objects are referenced through `rhi::Handle<T>` values, never raw pointers, across system boundaries.

### Render graph and extension points

The **render graph** (frame graph) is declared every frame. Each pass states which resources it reads and writes; the
graph then aliases transient memory, inserts barriers, assigns queues, and drops passes whose output nobody reads.

Render features inject passes at these named **extension points**, in frame order:

| Extension point | Typical passes |
|---|---|
| `PreDepth` | Depth prepass, Hi-Z build |
| `GBuffer` | Visibility buffer or G-buffer fill |
| `Lighting` | Clustered direct lighting |
| `GI` | Global illumination tiers |
| `Translucency` | Particles, glass, volumetrics |
| `PostProcess` | TAA/FSR, bloom, tone mapping |
| `UI` | Runtime UI canvases |
| `Debug` | Gizmos, overlays, GI debug views |

### Render world

The presentation layer **extracts** render data into a double-buffered `RenderWorld`. Rendering then runs one frame
behind the game thread without locks: the game thread fills one copy while the render thread consumes the other.

### Desktop pipeline: visibility buffer

The desktop renderer uses a **visibility buffer**: the geometry pass writes only a triangle and instance ID per pixel,
and materials are evaluated afterwards in deferred material passes. This was decision 4 in
[DESIGN.md §18](https://github.com/ugokce/Detergine-3D-ECS-Game-Engine/blob/main/docs/DESIGN.md#18-key-risks--open-questions)
(resolved 2026-11-05). The rest of the desktop path:

* GPU-driven visibility: meshlets built with meshoptimizer, compute culling (frustum plus Hi-Z occlusion), and
  `vkCmdDrawIndexedIndirectCount`.
* Clustered lighting, metallic/roughness PBR compatible with glTF.
* Cascaded or virtual shadow maps, TAA or FSR, bloom, tone mapping (ACES or AgX), SSAO/GTAO and SSR.

### Mobile pipeline: forward+

Android (and optionally iOS) uses **forward+** with tile-based light culling. Render passes are tuned for tile-based
deferred rendering (TBDR) GPUs: load and store operations avoid round trips to main memory. Textures are ASTC, shading
uses half precision, and GI is baked or probe-based. Apple Silicon is also a TBDR GPU, so both pipelines follow the same
tile-memory rules; macOS uses the desktop pipeline by default.

### Materials

Materials are Slang modules. Material instances are parameter blocks stored in a bindless buffer. A node-graph material
editor comes later.

### 2D rendering

* A sprite renderer with dynamic batching by atlas and material, Unity-like sorting layers and order, sprite animation,
  9-slice, chunked tilemaps, optional 2D lights, and a pixel-perfect camera.
* `SpriteAtlas` assets packed by the cooker with stb_rect_pack, with padding, extrusion and mip chains. UI text uses MSDF
  glyph atlases (see [Runtime UI](ui.md)).
* 2D and 3D share the RHI, render graph and camera stack, so mixed 2.5D scenes work.

### Global illumination (clean-room, Lumen-style)

> **Warning:** Unreal Engine source code is under the Unreal Engine EULA. Never copy it, its shaders, or line-by-line
> translations into this repository. The GI is a **clean-room implementation** of the published design from the
> SIGGRAPH 2022 Advances course talk on Lumen (Wright, Narkowicz, Kelly) and other public research. AMD's MIT-licensed
> FidelityFX Brixelizer GI and GI-1.0 may be used as code-level references.

The desktop tier ([DESIGN.md §8.5](https://github.com/ugokce/Detergine-3D-ECS-Game-Engine/blob/main/docs/DESIGN.md#85-global-illumination--lumen-style-design-clean-room))
uses software ray tracing, with hardware ray tracing as an option:

1. **Scene representation for tracing**
   * Per-mesh **signed distance fields** (sparse SDF bricks) generated at import, merged into a **global SDF clipmap**
     around the camera for long-range rays.
   * A **surface cache** of "cards": each mesh is captured from a few axis-aligned directions into an atlas of albedo,
     normal, emissive and depth, which makes material lookup at a ray hit cheap.
2. **Lighting the surface cache**: direct light is computed into the card atlas; multi-bounce comes from feeding the
   previous frame's GI back into the cards. Only a budgeted number of cards update per frame, prioritized by screen size
   and change.
3. **Final gather**: adaptive **screen-space probes** (about one per 16×16 pixels, refined at depth and normal edges)
   trace rays first in screen space (HZB), then against mesh SDFs (near) and the global SDF (far). A **world-space
   radiance cache** of clipmapped probes handles distant light. Probes are importance-sampled, filtered spatially and
   temporally, and integrated into pixels with bent normals.
4. **Reflections**: rough reflections reuse the probes; smooth reflections trace their own rays (after SSR) with the same
   surface-cache hit lighting.
5. **Hardware RT** (`DesktopRT` tier, `VK_KHR_ray_query`): BLAS/TLAS traces against simplified proxy geometry replace
   SDF tracing; the surface cache and final gather stay the same.
6. **Translucency and volumetrics**: a froxel volume samples the radiance cache.

Mobile and low tiers use **DDGI-style irradiance probe volumes** updated sparsely in compute, or **baked lightmaps**
(xatlas UVs, GPU baker in the editor) with reflection probes. Quality settings choose the tier per project and platform.

GI ships in four phases: **A** baked lightmaps and probes, **B** DDGI probes, **C** SDF + surface cache + screen probes,
**D** hardware RT.

## How it will be used

Most game code never touches the renderer directly. You put presentation components (meshes, lights, cameras,
sprites) on entities, and the extraction step copies them into the render world. Engine and plugin developers extend
rendering by writing an `IRenderFeature` that registers passes at an extension point instead of editing the core
pipeline. CLAUDE.md requires renderer changes to add or update a golden-image test where practical and to run clean
under the Vulkan validation layers.

The planned names above (`IRenderFeature`, `RenderWorld`, `rhi::Handle<T>`, the tier names) come from the design. None
of them exist in the code yet.

## Integration with existing code

These pieces exist today and are what the renderer will build on:

* **Render math** in [Matrix.h](engine/math/include/dg/math/Matrix.h) already follows the renderer's conventions:
  column-major storage that can be copied to a GPU buffer as is, a right-handed world with the camera looking down -Z,
  Vulkan clip space with depth range [0, 1] and Y pointing down (the projections flip Y, so the viewport keeps a
  positive height), counter-clockwise front faces, and **reversed-Z** depth for every projection (clear to 0, compare
  with `VK_COMPARE_OP_GREATER_OR_EQUAL`). See [Vectors, quaternions and matrices](../systems/vector-math.md).

```cpp
#include "dg/math/Matrix.h"

// Camera matrices in the conventions the renderer will consume: right-handed, reversed-Z, Vulkan clip space.
dg::Mat4 viewProjection(const dg::Vec3& eye, const dg::Vec3& target, dg::f32 aspect) {
    const dg::Mat4 view = dg::Mat4::lookAtRH(eye, target, {0.0f, 1.0f, 0.0f});
    const dg::Mat4 projection = dg::Mat4::perspectiveInfiniteRH(1.0472f, aspect, 0.1f); // 60 degrees
    return projection * view;
}
```

* **Headless builds**: the CMake option `DG_HEADLESS` (in [DgOptions.cmake](cmake/DgOptions.cmake), default `OFF`) is
  exposed to C++ as `dg::build::kHeadless` in [BuildInfo.h](engine/core/include/dg/core/BuildInfo.h). The renderer
  module must not be linked when it is on; headless builds will use a Null RHI. The runtime's `--headless` flag
  (`AppConfig::headless`) exists, but today it only changes a log line because there is nothing to turn off yet.
* **Handles**: `dg::Handle<Tag>` and `dg::HandlePool<T>` in `dg/core/Handle.h` are the model for `rhi::Handle<T>`
  (see [Generational handles](../systems/handles.md)).
* **Frame scratch**: `dg::LinearAllocator` with `mark()`, `rewind()` and `reset()` is the intended per-frame allocator
  (see [Memory allocators](../systems/memory.md)).
* **Strict floating point**: every engine target, including future render targets, is built with FMA contraction off.
  Render code may use `std::` math because it is not sim code; the strict flags exist to avoid ODR hazards for shared
  inline math (see [Determinism model](../architecture/determinism.md)).
* **Modules**: the renderer will be added with `dg_add_module(rhi ...)` and `dg_add_module(render ...)` in
  `engine/CMakeLists.txt`, after the sim modules and without the `SIM` flag, because rendering is presentation.

## Open risks

| Risk | Planned mitigation |
|---|---|
| MoltenVK/KosmicKrisp feature gaps on macOS (ray query, descriptor buffer, mesh shaders) | Capability tiers; the software GI path needs no RT; keep the RHI clean enough for a native Metal backend |
| Lumen-style GI complexity | Phased tiers with baked and DDGI first; time-boxed research spikes; AMD MIT references |
| Accidental IP contamination from Unreal code | Clean-room rule in CLAUDE.md: implement from public papers and talks only |
| TBDR bandwidth on Android and Apple GPUs | Forward+ mobile path and render passes with tile-friendly load/store ops |
